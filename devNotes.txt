#### Mental Model Breakdown

Let's break down why, based on the project's structure:

1.  **The Two "Worlds":** Your project has two distinct types of code:
    *   **PHP & Standard Assets:** This includes all `.php` files, the jQuery-based `.js` files (like `clisyc-admin-manage-slots-fc.js`), and the standard `.css` files (like `clisyc-admin-style.css`). These files are used "as-is" and are simply copied into the final plugin by the `build.sh` script.

2.  **The `npm` Build Step:** The command `npm run build` is a "compilation" or "transpilation" step. It tells the `@wordpress/scripts` tool to:
    *   Take the modern React/JavaScript source code from the `.../js/src` folders.
    *   Bundle it, optimize it, and transform it into browser-compatible JavaScript and CSS.
    *   Place these final, compiled files into the `.../js/dist` folders.

The files inside the `dist` directories are the only ones that WordPress actually loads with `wp_enqueue_script` and `wp_enqueue_style`.

#### Your Workflow Guide

    *   `src/pro/includes/modules/forms/js/src`
    *   `src/pro/includes/modules/outputs/js/src`
    *   **Action:** Run `npm run build`, then run `build.sh`.

*   **If you modify any .php file...**
    *   **Action:** Just run `build.sh`. You do not need `npm run build`.

*   **If you modify a .js or .css file NOT in a `.../src` subfolder...**
    *   e.g., `clisyc-admin-styles-page.js` or `src/assets/css/clisyc-admin-style.css`
    *   **Action:** Just run `build.sh`. You do not need `npm run build`.

*   **If you modify composer.json...**
    *   **Action:** Run `composer install` first, then run `build.sh`.

Before running tests for the first time, you must set up the test environment. This is a one-time command:

3.  **Installs WooCommerce:** The test suite depends on WooCommerce classes. This command downloads and installs the WooCommerce plugin into the temporary `tmp/` test directory so it's available to PHPUnit.

After the setup is complete, you can run the entire PHPUnit test suite at any time with:
`composer test`

#### Autoloading and Dependency Management (The Journey)

Getting the test suite to run reliably involved solving several layers of dependency issues. Here is a summary of what was tried and the final solution:

1.  **The Problem:** The initial test setup failed with "Class not found" fatal errors. This was because the WordPress test environment loads plugins in a way that bypasses standard Composer autoloading, and our plugin's classes were not being manually included.

2.  **Attempt #1 (PSR-4 Autoloading):** The first attempt was to implement the modern PSR-4 autoloading standard in `composer.json`. This failed because the plugin's file naming convention (e.g., `class-database-manager.php`) does not match the strict naming required by PSR-4 (which would expect `DatabaseManager.php`).

3.  **Attempt #2 (Classmap Autoloading):** The next attempt was to switch to Composer's `classmap` autoloader. This is more flexible as it scans directories and maps class names to file paths, regardless of the filename. However, this also failed within the PHPUnit bootstrap process, indicating a deeper conflict with how the WordPress test suite loads plugins and handles dependencies.

4.  **The Final Solution (Hybrid Approach):**
    *   We kept the **`classmap` autoloader** in `composer.json`. This is still a best practice for the live plugin, ensuring that when the plugin is active on a real site, its classes are autoloaded efficiently without manual `require_once` statements. The `build.sh` script correctly copies the `vendor` directory into the final plugin packages.
    *   We **restored the manual dependency loading** within the plugin's core `Plugin` class (`src/shared/includes/core/class-plugin.php`). The `load_dependencies()` method was reinstated to explicitly `require_once` all necessary class files.
    *   This method uses the `CLISYC_SHARED_DIR` constant, which intelligently points to the correct `shared/` directory whether running in the monorepo (for tests) or from a final built plugin directory.

This hybrid approach provides the best of both worlds: robust, explicit dependency loading for the unique context of the PHPUnit test suite, and modern, efficient autoloading for the live production environment.

# Relationship Graph System - Developer Documentation

## Overview

The Relationship Graph is a visual interface for managing relationships between dimension custom post types (CPTs) in the Client Sync plugin. It uses React Flow to provide an interactive node-based graph where administrators can:

- View all dimension posts (Services, Practitioners, Rooms, etc.) as nodes
- Create connections (edges) between posts to define which items can work together
- Visually organize the hierarchy through drag-and-drop positioning
- Save relationship configurations that control booking availability

**Business Logic:** A booking is only valid when ALL required dimensions are connected. For example, a "Heart Surgery" service can only be booked when a connected practitioner AND a connected room are both available.

## Database Structure

### Table: `wp_clisyc_relationships`

Stores the connections between posts (the edges in the graph).

```sql
CREATE TABLE wp_clisyc_relationships (
    relationship_id BIGINT(20) UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    parent_object_id BIGINT(20) UNSIGNED NOT NULL,
    parent_object_type VARCHAR(32) NOT NULL,
    child_object_id BIGINT(20) UNSIGNED NOT NULL,
    child_object_type VARCHAR(32) NOT NULL,
    UNIQUE KEY unique_relationship (parent_object_id, parent_object_type, child_object_id, child_object_type)
);
```

**Important:** Each relationship is stored ONCE in a single direction (parent → child). Do NOT create bidirectional duplicates.

**Example:**
```
parent_object_id: 123 (Service: "Heart Surgery")
parent_object_type: clisyc_service
child_object_id: 456 (Practitioner: "Dr. Smith")
child_object_type: clisyc_practitioner
```

### Table: `wp_clisyc_graph_nodes`

Index of all posts that appear as nodes in the graph.

```sql
CREATE TABLE wp_clisyc_graph_nodes (
    node_id BIGINT(20) UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    node_hash VARCHAR(128) NOT NULL UNIQUE,
    cpt_slug VARCHAR(32) NOT NULL,
    wp_post_id BIGINT(20) UNSIGNED NOT NULL,
    node_type VARCHAR(32) NOT NULL,
    label VARCHAR(255) NOT NULL,
    parent_hash VARCHAR(128),
    last_updated DATETIME NOT NULL
);
```

**Node Types:**
- `dimension` - The CPT type itself (e.g., "Services" - used for filtering, not displayed as a node)
- `postNode` - Individual posts (e.g., "Heart Surgery", "Dr. Smith")

**Node Hash Format:**
- Dimension: `clisyc_service`
- Post Node: `clisyc_service:123` (CPT slug + post ID)

### Option: `clisyc_graph_visual_state`

Stores the X,Y coordinates of each node for positioning.

```php
[
    'clisyc_service:123' => [
        'position' => ['x' => 100, 'y' => 50]
    ],
    'clisyc_practitioner:456' => [
        'position' => ['x' => 200, 'y' => 150]
    ]
]
```

### Backend (PHP)

**Purpose:** REST API endpoints for loading and saving graph data

**Key Methods:**

- `update_graph_data()` - Saves nodes, edges, and visual state to database

**Critical Logic:**
```php
// When saving edges, preserve direction (source → target)
// Do NOT normalize by ID or create reverse relationships
$wpdb->insert( $rels_table_name, [
    'parent_object_id'   => $source_id,    // Preserve as-is
    'parent_object_type' => $source_type,
    'child_object_id'    => $target_id,    // Preserve as-is
    'child_object_type'  => $target_type,
]);
```

#### `/src/shared/includes/admin/class-graph-node-manager.php`
**Purpose:** Maintains the graph_nodes index table

**Key Methods:**
- `rebuild_index()` - Rebuilds entire node index from scratch
- `handle_save_post()` - Updates index when a post is created/updated
- `handle_delete_post()` - Removes node when post is deleted

**Hooks:**
- `save_post` (priority 99) - After post is saved
- `before_delete_post` - Before post is deleted
- `update_option_clisyc_dimension_registry` - When dimensions change

#### `/src/shared/includes/services/class-importer.php`
**Purpose:** Imports pre-configured templates

**Critical Bug Fix:** Only create relationships in ONE direction (parent → child), never create reverse relationships.

```php
// CORRECT ✅
$wpdb->insert( $rels_table_name, [
    'parent_object_id' => $parent_id,
    'child_object_id' => $child_id
]);

// WRONG ❌ - Creates duplicate phantom edges
$wpdb->insert( $rels_table_name, [
    'parent_object_id' => $child_id,  // Reversed!
    'child_object_id' => $parent_id
]);
```

### Frontend (JavaScript/React)

#### `/src/assets/src/App.js`
**Purpose:** Main React component for the graph interface

**Key Features:**
- Loads graph data from REST API on mount
- Manages nodes and edges state with React Flow hooks
- Handles save operations
- Provides toolbar buttons (Auto-Layout, Connect All, etc.)

**Important Hook:**
```javascript
useEffect(() => {
    const fetchData = async () => {
        const { nodes, edges } = await apiFetch({ 
            path: '/clisyc/v1/dimensions/graph' 
        });
        
        setNodes(nodes || []);
        
        // CRITICAL: Delay edge setting to ensure nodes are registered first
        setTimeout(() => {
            setEdges(edges || []);
        }, 100);
    };
    fetchData();
}, [setNodes, setEdges, fitView]);
```

#### `/src/assets/src/PostNode.js`
**Purpose:** Custom node component for React Flow

**Key Features:**
- Renders node with title, icon, and dimension label
- Always includes BOTH top and bottom handles (for React Flow connections)
- Hides unnecessary handles with CSS for visual clarity

**Critical Implementation:**
```javascript
// Always render both handles (needed for React Flow to connect)
<Handle type="target" position={Position.Top} id="a" />
<Handle type="source" position={Position.Bottom} id="b" />
```

**Handle Visibility Rules:**
- Top handle on Services (first dimension): Should be hidden via CSS
- Bottom handle on Rooms (last dimension): Should be hidden via CSS
- All middle dimensions: Show both handles

## Data Flow

### Loading the Graph

```
1. User navigates to Dimension Manager → Relationship Graph tab
   ↓
2. React app mounts, useEffect triggers
   ↓
3. apiFetch GET /clisyc/v1/dimensions/graph
   ↓
4. PHP: get_graph_data() executes
   ↓
5. Query wp_clisyc_graph_nodes for all postNode records
   ↓
6. Query wp_clisyc_relationships for all edges
   ↓
7. Get clisyc_graph_visual_state option for positions
   ↓
8. Return JSON: { nodes: [...], edges: [...], visual_state: {...} }
   ↓
9. React: setNodes() and setEdges() (with 100ms delay)
   ↓
10. React Flow renders the graph
```

### Saving the Graph

```
1. User clicks "Save Changes" button
   ↓
2. handleSaveChanges() gathers current nodes and edges from React Flow
   ↓
3. apiFetch POST /clisyc/v1/dimensions/graph with payload:
   {
       nodes: [{ id, position, data }, ...],
       edges: [{ source, target }, ...]
   }
   ↓
4. PHP: update_graph_data() executes
   ↓
5. Extract positions from nodes → save to clisyc_graph_visual_state option
   ↓
6. TRUNCATE wp_clisyc_relationships table
   ↓
7. Loop through edges:
      - Parse source/target (format: "clisyc_service:123")
      - Verify both posts exist
      - Check for duplicates (both forward and reverse)
      - INSERT single directional relationship
   ↓
8. Return success response
   ↓
9. React shows success toast notification
```

## Critical Issues and Solutions

### Issue #1: Conditional Handle Rendering
**Problem:** Initially, handles were conditionally rendered based on filterOrder:
```javascript
{!isFirst && <Handle type="target" ... />}  // ❌ BAD
```

This caused newly created posts to have missing handles, so connections to them would disappear on page refresh.

**Solution:** Always render both handles, hide them with CSS when not needed:
```javascript
<Handle type="target" position={Position.Top} id="a" />  // ✅ GOOD
<Handle type="source" position={Position.Bottom} id="b" />
```

### Issue #2: Bidirectional Relationships
**Problem:** The importer was creating relationships in BOTH directions:
```php
// Forward
INSERT (parent: 123, child: 456)
// Reverse
INSERT (parent: 456, child: 123)  // ❌ Creates phantom edges
```

This caused "phantom connection lines" appearing in wrong directions.

**Solution:** Only create relationships in ONE direction (parent → child):
```php
// Only insert the relationship as defined in template
INSERT (parent: 123, child: 456)  // ✅ CORRECT
```

### Issue #3: Edge Loading Timing
**Problem:** Edges were set at the same time as nodes, causing React Flow to try rendering edges before nodes were registered.

**Solution:** Delay edge setting by 100ms:
```javascript
setNodes(nodes);
setTimeout(() => setEdges(edges), 100);  // ✅ Gives React Flow time to register nodes
```

### Issue #4: Auto-Connect on Empty Graph
**Problem:** When installing a template, the graph would auto-run "Connect All" if no edges existed, creating invalid connections (e.g., Service → Room directly, skipping Practitioner).

**Solution:** Removed auto-connect on load. Templates define their own relationships:
```javascript
// REMOVED this problematic code:
if (!edges?.length) {
    handleConnectAll();  // ❌ BAD
}
```

## Troubleshooting

### Problem: Connections Disappear After Refresh

**Possible Causes:**
1. Node missing from `wp_clisyc_graph_nodes` table
2. Handle missing or hidden on target node
3. Post was deleted or unpublished

**Debug Steps:**
```sql
-- Check if node exists in index
SELECT * FROM wp_clisyc_graph_nodes WHERE wp_post_id = 123;

-- Check if relationship exists
SELECT * FROM wp_clisyc_relationships 
WHERE (parent_object_id = 123 OR child_object_id = 123);

-- Check if post exists and is published
SELECT post_status FROM wp_posts WHERE ID = 123;
```

### Problem: Phantom Connection Lines

**Cause:** Duplicate relationships in database (both A→B and B→A exist)

**Solution:**
```sql
-- Find duplicates
SELECT 
    LEAST(parent_object_id, child_object_id) as id1,
    GREATEST(parent_object_id, child_object_id) as id2,
    COUNT(*) as count
FROM wp_clisyc_relationships
GROUP BY id1, id2
HAVING count > 1;

-- Delete duplicates (keep only parent_id < child_id)
DELETE FROM wp_clisyc_relationships
WHERE parent_object_id > child_object_id;
```

### Problem: Graph Shows No Nodes

**Possible Causes:**
1. No dimensions enabled with `frontend_visible: true`
2. Node index needs rebuilding
3. JavaScript error preventing render

**Debug Steps:**
```php
// Check dimension registry
$registry = get_option('clisyc_dimension_registry');
var_dump($registry['dimensions']);

// Rebuild node index
$graph_manager = new Graph_Node_Manager();
$graph_manager->rebuild_index();

// Check browser console for JS errors
// Look for React/React Flow errors
```

## Best Practices

1. **Never create bidirectional relationships** - Each connection should exist ONCE as parent→child

2. **Always preserve edge direction** - When saving, don't normalize based on ID comparison

3. **Delay edge rendering** - Give React Flow 100ms to register nodes before setting edges

4. **Always include both handles** - Even if hidden, handles must exist for React Flow to connect

5. **Rebuild index after bulk changes** - After imports, dimension changes, or data migrations:
   ```php
   $graph_manager->rebuild_index();
   ```

6. **Validate relationships** - Before inserting, verify both posts exist:
   ```php
   if (get_post($parent_id) && get_post($child_id)) {
       // Safe to insert
   }
   ```

7. **Use transactions for bulk operations** - When inserting many relationships:
   ```php
   $wpdb->query('START TRANSACTION');
   // ... multiple inserts ...
   $wpdb->query('COMMIT');
   ```
